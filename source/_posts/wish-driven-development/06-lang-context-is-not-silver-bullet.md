前一阵Claude3发布了之后，我觉得可以基于大模型能都能支持长上下文这个假设来进行一下许愿驱动开发了。我就去试验了一下长上下文，看看对许愿驱动开发会带来什么变化吗？

大概的做法就是在有了长上下文之后，我就可以把整个项目都放进去了，我正好在做一些对话UI的对话机器人试验性项目，有前后端、有多个模块，各种不同的agent，整体上由内核有插件，也算是有点复杂，整个项目去掉无关的内容，生成的整个上下文大概有1万两千行代码和文档。按照token算的话，大约不到100k。

各个平台上，如果想要支持大上下文，必须以文件的形式上传上去，那我们之前生成的上下文文件就很有用了，直接拖过去就可以了，我们可以把这个看做一个启动上下文。

经过一段时间的各种实验，我得出了一些使用心得，最近终于有空写出来分享给大家。

## 依然只能做一步推理

我曾经想试试大模型上下文全了是不是就可以做一些较大的任务，所以我试着把整个项目和项目的依赖都扔了进去之后，我提出了一个较为复杂的任务，比如，我想做一个小agent，就是把各种后台REST API封装为一个个表单。让用户可以不用使用UI，直接使用对话UI提交自己的表单完成公司里的一些电子流。

于是我就跟LLM说想写一个新的agent，根据项目里提供的数据来识别哪些是用户想完成的任务提交的表单之类的。因为所有的代码都给它了，我想看看他能不能完成。

结果呢，写的非常差，任务拆分的也很差。背后的原因可能是多种多样的，跟我下面说的可能都有点关系，但总之是不要幻想大上下文有了之后可以许一个笼统的愿望，然后AI可以完全自动的把这个事做完。

经过长时间的尝试后，我发现，其能完成的任务粒度大小依然跟以前一样。哪怕重构也是一样。你改个数据结构，哪怕所有的代码都给了，让它重构，如果涉及到的代码多了，他依然会漏，不得不还是一小步一小步的驱动它改。

即便我们给了大量详细的任务描述，它在执行的时候要么会忽略掉一些重点，你需要反复把已经给出的、但被他漏掉的、任务描述里的重点在多轮对话中对话再次扔给他；要么会给出一个粗略的描述，你需要逐个让它细化。最大的体验就是他依然只能做一步推理，做完推理后，我们把符合期望的代码贴回去再更新上下文是更常用的做法。

所以用LLM写代码的核心能力还是拆出粒度合适的任务。

## 对任务的精确性要求变高了

我们之前说过，只要给出合适的上下文，那么我们的任务自然是没有歧义的。那这个逻辑背后也意味着，如果上下文大了，我们的任务自然就变得有歧义了。所以随着上下文增大，也确实证明了存在这个问题。

我们的项目结构里，每个agent是一个模块，这个模块式作为一个插件插入到我们的对话UI的内核中的。那在这种情况下，比如当我说要加一个pipe去实现某功能的时候，这个功能只要稍微通用一点，你就一发现大模型不一定给你生成到哪个模块去了。甚至于它可能生成的都不属于任何模块，就是重新写了一个通用的，哪个依赖都没用。

所以这导致我们要明确说明要针对哪个模块、哪个文件夹、甚至哪个文件、哪个类来定义任务，也就造成了我们对任务的精确性要求变高了，这其实造成了开发人员的负担。

## 不要过度依赖多轮对话，适时更新上下文

当我把长上下文的prompt扔给大模型后，那里面按照我们之前所说的包含了所有的文件夹树和文件的内容。我们可以肯定大模型可以精确识别每一个文件内容、文件的path和文件树的对应（具体提示词大概长什么样参考前面几篇）。所以我们产生了一个观点，那就是既然我提的每一个提问和大模型建议的修改都在对话历史里，那也就都在上下文里，那理论上在我达到200k下文上限之前我可以一直提问，反正所有的修改LLM都知道。

然而实际上证明这个观点是错的。我扔了一个约60k上下文的提示词，进行不到10轮对话，他就开始有幻觉了，回答的错误就比较严重。这时我做了一个试验，我问他上下文里某个文件的内容，他就明显是编造的了。

不知道是这些客户端的问题还是什么问题，总之我们依然需要适时的更新上下文，不能就一个启动上下文问特别多。

## 文档依然需要

当我们把所有的代码都扔给大模型之后，我们曾经天真的以为文档什么的就不需要了，大模型反正都能从代码中理解出来，但事实上我们错了。

尽管我们在过程中发现大模型对代码的理解能力远远超过文档，但是有很多文档所表达的信息是散列在代码中的，比如，我们的这个对话机器人，我自己搞的时候有一个类似chatgpt中thread的数据结构。他某一个版本的样子类似于：

```json
{
  id: "thread_id",
  agent: "对话机器人的name"
  messages: [
    {
        "id": "msg_0pyn9t1nx",
        "sender": "bot",
        "text": "回复: 需要按钮",
        "isHtml": false,
        "additionalData": {
          "buttons": {
            "属性1": true,
            "属性2": false
          }
        },
        "timestamp": 1708313881069
      }
  ]
}
```

从数据结构我们就能猜出来，这里面可以处理的场景不少，这些场景是各种不同的agent里的，但是总之都在整个代码上下文里。而因为我的代码是js的，所以我是没有准备一个类表达这个thread的数据结构的。

那么这个时候，尽管对所有属性的操作代码都已经给了大模型了，但因为是散列在多处的，实际上大模型并不能自己总结出这个数据结构。这种时候我们就需要专门准备一个文档。

另外有时候这么多的代码，到底是怎么分层分区的这种逻辑概念，你也不能指望大模型看完了就能自动抽象出来，也还是要准备文档的，否则它会出现理解错误。

所以，目前来讲，文档依然是需要的。

## 框架使用的挑战

我们在日常开发中，其实都是会自己做一些小框架类型的代码。比如我自己基于mocha包了一个数据驱动的测试框架，前面几篇里还提到自己做了一个pipeline框架来替代langchain。

在以前呢，这些框架最大的价值是减少开发难度、提升人的开发效率，而随着我们有了大语言模型，这些框架让大模型用起来肯能是个难题。

早期token数太少，我们的框架代码放不进去。现在随着上下文的增大，框架代码倒是能放进去了，但是大模型未必按照你期望的去用框架，他经常搞不清楚某个场景下是需要使用框架的。

应用框架需要你一步步的指导着LLM去做，这又进一步增大了开发人员的负担，不过好在，我们找到一些解决方案，我们后面的文章分享。
